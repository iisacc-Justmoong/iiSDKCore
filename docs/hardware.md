# Native hardware I/O (0.6.0)

`ii::io::Hardware` connects device discovery, topology changes, standard control commands and media I/O to an existing `EventLoop`. Public contracts use C++23 values and callbacks; operating system handles, Objective-C objects and WinRT objects stay private. `Hardware` and public records are final. Platform implementations are separate translation units and do not depend on Qt or upper iiSDK modules.

## Standards and scope

USB setup packets use the standard eight-byte little-endian control request format. `usb_control` supports standard, class and vendor requests through the OS USB host API. `usb_device_descriptor` decodes the standard device descriptor. Opening an endpoint does not detach a kernel driver or seize a device. Isochronous and bulk USB stream APIs are outside this version.

HID uses [USB-IF HID 1.11 and HID Usage Tables 1.7](https://www.usb.org/hid), current when checked on 2026-10-06. The report descriptor parser supports short items, bounded global push/pop, usage pages/ranges, report IDs, collection nesting, input/output/feature fields, constants, arrays and signed packed values. Long items and unknown usages remain uninterpreted. The layout preserves numeric usage IDs rather than a fixed list of known products. `HIDLayout::decode/encode` uses actual bit widths and checks truncation, numeric ranges and duplicate assignments. Descriptor limits are 64 nesting levels, 65,536 bits per report and a caller-specified field cap (4,096 by default). Physical units, resolution scaling and named controls remain consumers' responsibilities.

Bluetooth support is **Bluetooth LE central/GATT**: filtered service scanning, connection, characteristic read/write and notification subscription. UUIDs accept 16-, 32- and canonical 128-bit forms and are normalized to 128-bit text in events. The parser includes advertising AD length/type/value records (unknown types are preserved) and the standard Heart Rate Measurement characteristic. Bluetooth Classic RFCOMM, pairing UI, peripheral/server mode and arbitrary vendor profile semantics are outside this API. The relevant OS contracts are [CoreBluetooth](https://developer.apple.com/documentation/corebluetooth/cbcentralmanager), [BlueZ GATT](https://bluez.readthedocs.io/en/latest/gatt-api/) and [Windows GATT](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/gatt-client).

Audio transfers interleaved float32 PCM, normally at 48 kHz, with explicit channel count and frame capacity. `audio_write` returns **samples**, not frames or bytes, and accepts partial writes. Capture events carry `samples`. `pcm_s16le` converts signed 16-bit little-endian PCM with finite-value validation and saturation. It does not implement synthesis, effects, file codecs or an audio mixing graph. Linux uses [ALSA PCM](https://www.alsa-project.org/alsa-doc/alsa-lib/group___p_c_m.html), including a configured PipeWire ALSA plugin when the host chooses one; this is not a native PipeWire graph client.

MIDI transports native-endian 32-bit [Universal MIDI Packets](https://midi.org/midi-2-0) of one to four words. The framing decoder preserves message type and group, and the note decoder handles MIDI 1.0 and 2.0 notes. `MIDI1Decoder` supports incremental running status, interleaved realtime, bounded SysEx, status interruption and reset after malformed input. Reserved realtime bytes are ignored. `midi1_ump` converts individual channel/system messages; it does not segment SysEx byte streams into UMP. Native UMP transport passes SysEx7/SysEx8 and other well-framed packets unchanged; interpretation of their manufacturer payload is up to the consumer. Timestamp scheduling, MIDI-CI, property exchange and protocol negotiation are outside this version.

## Platform backends

| Platform | USB/HID and topology | Bluetooth LE | Audio | MIDI |
|---|---|---|---|---|
| macOS | IOUSBHost control, IOHIDDevice reports/descriptor; IOKit matching/removal notifications | CoreBluetooth central, asynchronous service/characteristic discovery | AudioQueue float32, CoreAudio device IDs and device-change notifications | CoreMIDI protocol 2.0 receive/send, topology notifications, virtual source/destination |
| Linux | libudev enumeration/monitor, usbfs control, hidraw descriptor/input/output/feature ioctls | BlueZ system D-Bus ObjectManager, discovery filters, GATT and property notifications | ALSA PCM nonblocking read/write, udev sound topology | ALSA UMP sequencer, announcements and virtual ports |
| Windows | SetupAPI device interfaces, Configuration Manager notifications, WinUSB control, overlapped HID input and HidD reports | C++/WinRT BLE advertisement watcher and GATT | WASAPI shared-mode float32, MMDevice IDs and device watcher | `Windows.Devices.Midi2` UMP when projections/service exist; otherwise deployed WinRT MIDI 1.0 ports |
| iOS | Generic USB host and raw HID APIs unavailable | CoreBluetooth | AudioQueue on the default session route; route-change notifications | CoreMIDI UMP and virtual endpoints |
| Android / WASM | No Hardware device-family backend in this version | unsupported | unsupported | unsupported |

The Android/WASM limitation applies to `Hardware`; existing Channel file/serial paths retain their documented capabilities. Protocol parsers and bounded dispatch state are portable and build on these targets. A browser WebUSB/WebHID/WebBluetooth/WebAudio/WebMIDI permission bridge and Android USB/Bluetooth/AAudio/AMidi host integration have not been implemented. An unsupported operation returns `ErrorCode::unsupported` rather than simulated device data.

`hardware_capabilities()` reports compiled API support, not the presence of a controller, service, driver or permission. Enumeration may return an empty list or an availability error. IDs are OS-local endpoint identities and must not be assumed portable across computers. BLE discovery additions are radio observations; disappearance from scan results does not prove physical unplugging. Connection loss is a separate event. `watch(bluetooth)` is invalid: start a scan with explicit service UUID filters instead.

### Build and host requirements

Linux requires development/runtime libudev, libdbus-1 and ALSA **1.2.10 or later**. UMP sequencer support requires a compatible kernel (introduced in Linux 6.5); see [kernel MIDI 2.0 documentation](https://docs.kernel.org/sound/designs/midi-2.0.html). The installed CMake package propagates these dependencies for static consumers. Hardware access follows udev permissions and BlueZ D-Bus policy. HID ioctl sizes above 16,383 bytes are rejected to avoid encoding size overflow.

Windows requires Windows SDK C++/WinRT headers. Native UMP is compiled when `winrt/Windows.Devices.Midi2.h` and its enumeration projections are available, and demands a running/available Windows MIDI Service through `MidiApi::EnsureServiceAvailable()`. Without these new SDK projections, the deployed `Windows.Devices.Midi` API supplies MIDI 1.0 input/output and DeviceWatcher hotplug. `hardware_capabilities().midi` remains true and `midi2` is false. MIDI 1.0 channel/system packets in group zero round-trip through the byte transport. Other groups, MIDI 2.0 packets and SysEx UMP segmentation are rejected rather than silently downconverted. The optional MIDI 2.0 path and the MIDI 1.0 path are explicit compiled capabilities; neither uses WinMM. The new in-box API rollout has platform/version requirements; availability must be verified on the target machine. See the [official SDK overview](https://microsoft.github.io/MIDI/sdk-overview/) and [current Microsoft C++ sample](https://github.com/microsoft/MIDI/blob/main/samples/cpp-winrt/static-enum-endpoints/main_static_enum_endpoints.cpp). Windows virtual MIDI creation is unsupported in this version.

For WinUSB, the device must expose an interface bound to the WinUSB driver. Physical USB enumeration by itself does not imply that its returned physical device path supports `WinUsb_Initialize`. Set `HardwareOptions::usb_interface_guids` to the canonical GUIDs exposed by that driver's INF/descriptor; enumeration and hotplug then include those functional interface paths. This follows the [official WinUSB contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/using-winusb-api-to-communicate-with-a-usb-device). Windows provides HID parsed capabilities but no raw report-descriptor retrieval through HidD, so `hid_descriptor` is unsupported there; supplied descriptors still work with the common parser. Feature/input reads and feature/output writes are supported, subject to native driver permissions.

Apple hosts declare `NSBluetoothAlwaysUsageDescription` before scanning and `NSMicrophoneUsageDescription` before capture. Missing usage descriptions return `permission_denied` before starting the corresponding service. The host handles OS consent and applicable sandbox entitlements. macOS HID may require Input Monitoring permission. iOS hosts configure and activate their `AVAudioSession`; the SDK does not replace the application's category/route policy. No permissions are bypassed by enumeration or opening.

## Delivery, capacity and removal

Native callbacks copy/enqueue data; user handlers execute on the EventLoop dispatcher. A periodic task collects native input/topology and dispatches a bounded batch, normally every 2 ms. `poll` must be pumped by the host, or a joined worker may run `run`. The interval is a cooperative target, not a hard latency guarantee. This hub currently uses one periodic slot rather than registering every native handle into the Channel poll set.

`HardwareOptions` bounds queued events, active endpoints, total dynamic payload per event, dispatch batch and interval. The default event/endpoint cap is 256 and per-event dynamic payload is 65,536 bytes, including bytes, PCM samples, UMP records and strings. Full/oversized events are dropped and counted in `HardwareStats::dropped`. Events admitted to the queue preserve FIFO order; topology events can also be dropped, so consumers reconcile with enumeration after overflow. BlueZ in-flight requests are bounded by the event cap. Returned enumeration vectors are snapshots and are not charged to the event queue.

Apple native command/collector/destructor entry points and the private MIDI worker own autorelease pools, so command-line and C++ worker hosts do not leak temporary Foundation objects through a missing GUI pool. Apple audio callbacks use preallocated single-producer/single-consumer rings and AudioQueue buffers. They neither allocate nor lock to transfer samples. Overrun is reported from the collector; output starvation emits silence. Other native callback families may allocate bounded payload copies and use the queue mutex. The EventLoop is not the audio realtime thread. Linux and Windows use nonblocking PCM pumps/available-buffer writes. ALSA buffer capacity/latency is negotiated by the OS; `queued_frames` is a requested capacity, not an exact guarantee on all drivers.

The pure parser `midi1_message` rejects group loss, invalid data bits, and MIDI 2.0 downconversion when converting UMP for a byte-only port. Commands are serialized per hub and return typed errors. USB controls have an explicit 1–60,000 ms deadline. Native control calls and some OS enumeration/GATT calls can block; submit them to a Runtime/SerialQueue worker when the host requires responsive GUI/game dispatch. Windows media/WinRT commands require a host-initialized MTA caller and return `busy` from an STA or an uninitialized thread. The host keeps COM initialized until it has closed all hubs and released their media references, and closes those references from an initialized MTA. The SDK does not initialize/uninitialize COM around an individual call while retaining references beyond it. Already-running native calls are not preempted by the EventLoop time budget.

`close(endpoint)` releases native device/session resources, unregisters endpoint callbacks, removes its queued events, suppresses late responses and waits for active user delivery to finish. Its slot is reusable only after delivery completes. `close()` stops admission, cancels the periodic token, quiesces dispatch, shuts down all native sources, destroys queued events and the handler, and returns the loop slot. Concurrent hub close is serialized and repeated close succeeds. Own-callback close returns `busy`. A Runtime worker also receives `busy` if hub close would wait for active foreign dispatch; an owner thread must finish that close after dispatch quiesces. Destroying a hub while its close cannot finish violates the lifetime contract and terminates. The borrowed EventLoop must outlive the hub. Destruction invokes the same clean close path.

OS disconnect/stop commands can complete asynchronously (notably BLE); a successful local close proves the SDK has released its own endpoint and dispatch state, not that a remote peripheral has already observed the disconnect. CoreMIDI topology notifications use a private CFRunLoop on an owned `Thread`, shared by active MIDI hubs and stopped/joined when the last hub closes. This allows headless EventLoop execution without pumping a GUI run loop. CoreMIDI may retain its original process notification context after all clients close, so watched MIDI topology also reconciles native enumeration every 100 ms. Notifications trigger an earlier scan; periodic reconciliation preserves addition/removal after complete pump recreation. Timing still depends on host pumping and native call duration. A host that initialized CoreMIDI earlier must keep its own original native notification run loop alive. Removing a MIDI virtual endpoint removes it from OS enumeration. Shared OS devices, pairing records, external storage and process allocator pages are not owned by this hub. Memory wiping and immediate RSS reduction are not removal guarantees.

## Usage and verification

```cpp
#include <iiSDKCore/IO/Hardware.h>
ii::runtime::EventLoop loop(64);
ii::io::Hardware hardware(loop, [](ii::io::HardwareEvent event) {
    if (!event.midi.empty()) {
        auto note = ii::io::protocol::note(event.midi.front());
        if (note) { /* consume only the required fields */ }
    }
});
auto inputs = hardware.enumerate(ii::io::DeviceKind::midi_input);
if (inputs && !inputs->empty()) {
    auto endpoint = hardware.open_midi(inputs->front().id);
    // Pump loop.poll(), then close the endpoint outside its callback.
}
```

`examples/hardware.cpp` performs read-only inventory without starting a scan or microphone. `tests/protocols.cpp` covers binary formats and malformed input. `tests/hardware_state.cpp` covers combined payload/capacity, stale callbacks, active-delivery quiescence, quota reuse and concurrent audio-ring order. `tests/hardware.cpp` checks public validation and available native enumeration; on macOS it creates a CoreMIDI destination, observes addition, sends MIDI 2.0 UMP through the OS, receives it through EventLoop, observes removal, and repeatedly reuses endpoint capacity. The test also closes every MIDI hub, recreates the native notification pump, receives another OS-routed message, and checks addition/removal again. Installed consumers repeat public protocol/hardware contracts. Source/build, native execution, cross-compilation and physical-device evidence are recorded separately in [validation.md](validation.md).
