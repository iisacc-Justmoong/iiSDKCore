# 세션과 런타임 객체 수명

`ii::runtime::Session`은 특정 제품의 계정이나 문서가 아닌, 작업과 객체의 공통 수명 경계다. 세션은 하나의 `Runtime`에 등록되며 자신의 작업과 객체를 가진다. 런타임에도 별도의 `ObjectOwner`가 있어 여러 세션보다 오래 살아야 할 객체를 직접 소유할 수 있다. 두 소유자는 독립적이다.

```cpp
ii::runtime::Runtime runtime({.workers=1});
auto shared = runtime.objects().emplace<Cache>();
auto session = runtime.create_session();
auto document = session->objects().emplace<Document>();
if (shared && document) {
    auto submitted = session->post(runtime, [document = *document] {
        (void)document.with([](Document& value) { value.refresh(); });
    });
    // 접수 실패와 작업 결과는 호출자가 처리한다.
    (void)submitted;
}
auto closed = session->close();
auto stopped = runtime.join();
```

## 소유와 접근

`ObjectOwner::emplace<T>`는 객체를 생성하고, `adopt(std::unique_ptr<T>)`는 기존 객체의 독점 소유권을 넘겨받는다. 소유한 타입의 소멸자는 `noexcept`여야 한다. 반환되는 `ObjectRef<T>`는 소유자가 아닌 약한 핸들이다. `with(callback)`이 성공한 동안에만 `T&`를 사용할 수 있으며 참조·포인터를 콜백 밖으로 보관해서는 안 된다. 종료되거나 제거된 핸들은 `SubmitError::stopped`를 반환한다. 핸들은 객체나 세션의 수명을 연장하지 않는다.

`expired()`는 새 접근이 가능한지를 보고하며, `true`인 동안에도 이전에 시작한 접근이 끝나기를 기다리는 객체는 아직 물리적으로 살아 있을 수 있다. `Runtime::objects()`와 `Session::objects()`가 반환하는 소유자 참조는 각각 해당 런타임 또는 세션 인스턴스가 존재하는 동안에만 유효하다.

여러 `with` 콜백은 동시에 실행될 수 있다. 수명 장벽은 객체 내부의 데이터 경쟁을 해결하지 않으므로, 변경 가능한 객체의 동기화나 직렬 실행은 호출자가 책임진다. 콜백에서 발생한 예외는 호출자에게 전달되며 접근 장벽은 정상적으로 해제된다. 객체 내부에서 별도로 공유한 파일·GPU 자원 등의 외부 소유권까지 강제로 회수하지는 않는다.

`erase(handle)`은 같은 소유자의 객체 하나를 제거하고, 진행 중인 해당 객체 접근이 끝난 뒤 소멸자를 완료한다. 잘못된 소유자·오래된 핸들은 `invalid_work`, 자기 자신의 접근 안에서 제거하면 `self_join`, 다른 제거가 진행 중이면 `busy`다. 기다릴 수 없는 작업자나 브라우저 호스트에서는 `would_block`을 반환할 수 있다. 그 경우 해당 객체의 새 접근은 이미 닫혔을 수 있으며, 외부 스레드에서 `erase` 또는 소유자 종료를 다시 시도한다. `adopt`는 닫힘과 경합해 실패해도 전달받은 `unique_ptr`을 소비하고 파괴한다. `emplace`도 종료와 경합하면 생성한 객체를 즉시 파괴하고 `ObjectError::closed`를 반환할 수 있다.

## 세션 종료

세션은 `active → closing → closed` 상태를 갖는다. `request_close()`는 stop token을 요청하고 세션 작업과 객체 접근의 새 접수를 닫으며 대기 중인 세션 작업을 취소한다. 이미 실행 중인 콜백은 강제 중단되지 않는다. 작업은 `stop_token()`을 확인해 협력적으로 중단할 수 있다. 세션의 `post`·`at` 또는 약한 `sender()`로 등록한 작업만 이 장벽에 포함된다.

`close()`는 진행 중인 세션 작업·캡처와 객체 접근이 끝날 때까지 기다린 다음, 남은 객체를 부착 역순으로 파괴한다. `closed`는 이 정리가 끝난 후에만 설정된다. `try_close()`는 진행 중인 작업이나 접근을 기다리지 않고 `would_block`을 반환하지만, stop callback, 대기 작업의 캡처와 이미 정리할 수 있는 객체의 소멸은 호출 스레드에서 동기적으로 수행하므로 실행 시간이 0이라는 뜻은 아니다. 두 종료 메서드는 반복 호출할 수 있다.

자신의 세션 작업이나 소유 객체의 `with` 안에서 `close()`를 호출하면 접수 상태를 바꾸기 전에 `self_join`을 반환한다. 이런 코드에서는 `request_close()`만 호출하고 외부 문맥에서 `close()`를 마무리한다. 소멸자는 최종 장벽을 수행한다. 따라서 소멸자를 자기 콜백 안에서 실행하거나 기다릴 수 없는 스레드에서 활성 작업이 남은 상태로 실행해서는 안 된다.

## 런타임 종료와 순서

`Runtime::request_stop(drain)`은 기존처럼 새 런타임 작업 접수를 닫고 이미 접수된 작업을 실행한다. 이 단계에서는 세션 객체와 런타임 객체가 유지되므로 drain 중인 작업이 사용할 수 있다. 새 세션 생성은 종료가 시작된 뒤 거부된다. `cancel_pending`은 기존 계약대로 대기 중인 런타임 작업을 취소한다.

`Runtime::join()`은 워커 작업과 캡처가 모두 끝난 후 살아 있는 세션을 생성 역순으로 닫고, 마지막으로 런타임 소유 객체를 부착 역순으로 파괴한다. 세션이 다른 실행기에 등록한 대기 작업도 이때 취소하고 활성 작업을 기다린다. 실행 중인 콜백이 협력적으로 끝나지 않으면 종료도 기다린다. 작업 실패를 보고할 때에도 객체 정리는 수행한다. 세션 핸들은 런타임보다 오래 살아도 안전하지만 이미 닫힌 상태이며 객체를 다시 열 수 없다.

해당 런타임의 작업자나 정리 중인 캡처, 런타임 소유 객체의 접근, 또는 그 런타임에 속한 세션의 작업·객체 접근 안에서 `join()`하면 `self_join`을 반환한다. 다른 런타임의 작업자 등에서 기다려야 하는 경우 `would_block`을 반환할 수 있다. 이때는 외부 스레드에서 `join()`을 다시 호출해야 하며, 이전 호출이 워커를 이미 결합했어도 남은 세션과 객체를 정리한다. `request_stop`이나 `wait_idle`만으로 소유 객체가 파괴되지는 않는다.

소멸은 종료·제거를 실행한 스레드에서 일어난다. UI 스레드 또는 GPU 문맥에 고정된 자원은 해당 스레드에서 종료를 조정해야 한다. 등록하지 않은 작업이 차용 참조를 별도로 보관한 경우 이 API는 그 작업의 수명을 추적할 수 없다.
