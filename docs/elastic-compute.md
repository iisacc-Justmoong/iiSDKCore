# 컴퓨팅 자원의 동적 수명

## 실행 워커

`Runtime::resize_workers(count)`는 해당 Runtime이 소유하는 실제 워커 스레드의
수를 명시적으로 변경한다. 양의 값으로 늘리면 워커를 시작하며, 줄일 때는 선택된
워커가 현재 콜백과 캡처의 정리를 마친 뒤 종료한다. 이미 접수한 작업을 강제로
중단하거나 다른 장치로 이주시키지 않는다. 0은 새 접수를 막고 이미 접수된 작업을
마친 뒤 모든 워커와 작업 슬롯 저장소를 반환한다. 이후 양의 값으로 복구할 수 있다.
기본 Runtime은 워커와 작업 슬롯을 할당하지 않으며, `Runtime::allocated_slots()`로
현재 확보한 작업 슬롯 수를 확인한다. 워커가 없거나
0으로 줄이는 도중의 제출은 `SubmitError::overloaded`다. 큐의 용량과 개수, 토큰,
객체별 순서 및 기존 작업의 접수 책임은 보존한다.

축소는 진행 중인 콜백 종료를 기다리므로 자신의 Runtime 워커에서는 `self_join`,
안전하게 기다릴 수 없는 브라우저·호스트 루프에서는 `would_block`을 반환한다.
종료 또는 다른 크기 변경과 겹치면 `busy`, 이미 종료 중인 실행기는 실패한다.
워커 수가 `Runtime`의 작업 슬롯 용량을 넘는 요청은 거절한다. 증설이 실패하면
새로 시작한 스레드를 반환하고 기존 워커 수를 보존한다. `RuntimeStats::workers`는
신규 작업을 받을 수 있는 워커 수다. 축소가 시작되면 목표 수를 즉시 알리며 기존
스레드는 실행 중인 작업을 마친 뒤 종료한다. 0으로 바꿀 때에는 새 접수도 닫는다.
성공한 변경은 기존 상태
관측에 통지한다. `ComputeRouter`는 워커가 0인 실행기에 신규 작업을 배치하지 않는다.

이 계약은 CPU 코어의 독점, OS 스케줄러 선점, 실행 중인 콜백의 중단, GPU 워커나
원격 호스트의 생성·이동을 약속하지 않는다. OS가 스레드 생성을 거부하면 오류를
돌려준다.

객체는 필요한 자원을 직접 구성하고 세션 소유자에 부착할 수 있다. 다음 객체의
워커와 메모리 블록은 해당 객체가 제거될 때 함께 정리된다. `allocate()`와 `emplace()`의
실패는 호출자가 처리해야 한다.

```cpp
struct ImportResources final {
    ii::runtime::Runtime workers{{.workers=1, .capacity=8}};
    ii::runtime::MemoryPool memory{1024 * 1024};
    ii::runtime::MemoryBlock buffer;
};

ii::runtime::Runtime base; // 이벤트·세션을 위한 소유자이며 워커는 없다.
auto session = base.create_session();
auto resources = session->objects().emplace<ImportResources>();
if (resources) {
    (void)resources->with([](ImportResources& value) {
        auto block = value.memory.allocate(4096);
        if (block) value.buffer = std::move(*block);
    });
}
auto result = session->close(); // 객체와 소유한 자원을 정리한다.
```

객체 밖으로 별도로 이전·공유한 블록이나 사용자가 만든 외부 GPU·OS 자원은 그
자체의 소유 규칙을 따른다. 이것은 프로세스의 모든 할당을 자동 추적하거나 다른
객체의 자원 사용을 강제로 제한하는 전역 정책이 아니다.

## 호스트 메모리

`MemoryPool`은 프로세스의 정렬된 호스트 메모리를 실제로 할당하며 바이트 상한과
사용량을 관리한다. `MemoryBlock`은 이동 전용 소유권이며 마지막 소멸 또는 명시적
해제로 할당을 반환한다. 풀 객체가 먼저 사라져도 블록과 그 회계 상태는 살아 있다.
풀의 한도는 살아 있는 할당보다 작게 줄일 수 없으며, 할당이 없으면 0으로 닫고
나중에 다시 늘릴 수 있다. 풀은 서로 다른 블록의 동시 할당·해제를 직렬화한다.
사용량과 최고 사용량은 시스템 할당이 진행 중인 예약까지 포함한다.

블록의 크기 변경 및 다른 풀로의 이동은 대상 저장소를 먼저 확보하고 공통 범위의
바이트를 복사한 다음 원본을 반환한다. 대상 할당이 실패하면 원본·크기·회계가
바뀌지 않는다. 이 과정에서 원본과 대상의 임시 추가 메모리 여유가 필요하다.
블록별 접근·이동·크기 변경을 경쟁시키지 않으며, 반환된 span은 다음 변경 또는
소멸 이후 사용할 수 없다. 이는 호스트 메모리 소유권과 데이터의 복사 이동이며,
물리 RAM의 독점·GPU 장치로의 투명한 이전이나 원격 기기 전송을 의미하지 않는다.
C++의 새 메모리와 크기가 늘어난 뒷부분은 초기화되지 않으므로 읽기 전에 써야 한다.

## Python과 C

공유 iiSDKCore 라이브러리를 제공하는 데스크톱 환경에서는 설치된
`share/iiSDKCore/python/iisdkcore_resources.py`의 `Library(공유_라이브러리_경로)`로
같은 네이티브 풀, 블록과 Runtime 워커를 소유·조작한다. Python 블록의 새 메모리와
크기가 늘어난 뒷부분은 0으로 초기화한다. `with` 또는 `close()`로 명시적으로
해제할 수 있고, 블록은 풀 핸들보다 오래 살 수 있다. 동일한 블록을 여러 스레드가
수정하는 동시 접근은 호출자가 동기화한다. Python Runtime의 `workers`와
`allocated_slots`는 각각 할당된 워커 수와 작업 슬롯을 조회한다. `runtime(workers=0)`은
워커를 만들었다가 종료하지 않고 처음부터 할당하지 않는다.
macOS와 Linux의 공유 빌드는 설치된 Core와 같은 디렉터리에서 Observation 공유
라이브러리를 찾도록 설정되어 별도의 라이브러리 검색 경로가 필요하지 않다.

`Runtime/ResourceControlC.h`는 같은 기능의 C ABI를 제공한다. 0이 아닌 오류 코드를
반환하고 C 경계를 넘어 예외를 전달하지 않는다. C 핸들은 해제 후 사용하거나 두 번
해제하지 않으며, 다른 스레드의 사용 중에는 파괴하지 않는다. Python은 이 C ABI를
`ctypes`로 호출하고 Core 런타임에 Python 의존성을 추가하지 않는다. iOS와 WASM의
정적 빌드에 데스크톱 Python 공유 라이브러리가 생기는 것은 아니다.
Python 인터페이스는 워커와 호스트 메모리를 다루며, 아래의 협력적 작업 전이는
현재 C++ 인터페이스로 제공한다.

## 협력적 작업 전이

`MigratingWork`는 호출자가 지정한 작업 종류·버전과 소유 바이트 상태를 실행기에
제출한다. 작업 단계는 이전 상태를 읽고 다음 상태 또는 완료 결과를 반환한다. 이동·
일시 중지 요청은 현재 단계가 돌아온 후에만 적용한다. 목적 실행기 접수가 실패하면
마지막 체크포인트는 일시 중지 상태로 남고 명시적으로 재시도할 수 있다. 실행 중인
임의의 C++ 스택이나 이미 제출된 GPU 명령을 강제 선점하지 않는다.

한 작업의 연속 단계는 완료·중지·전이 시점까지 같은 워커를 점유한다. 따라서 단계
하나를 짧고 유한하게 만들고 장시간 작업이 다른 작업의 실행을 지연하지 않도록
실행기를 적절히 분리해야 한다. 단계마다 자동으로 공정한 재배치를 수행하지 않는다.

일시 중지한 작업은 체크포인트를 추출해 원래 작업의 재개 권한을 넘길 수 있다.
체크포인트는 크기가 제한된 버전·작업 종류·단계·바이트 데이터로 인코딩하며,
수신 측이 같은 종류와 버전의 구현을 공급해야 한다. 복원 접수에 실패하면 입력
체크포인트는 보존된다. 서로 다른 장치·프로세스는 인증된 전송과 작업 구현 배포,
중복 방지 및 소유권 펜싱을 별도로 제공해야 하며 직렬화된 바이트 자체는 단독
소유권이나 정확히 한 번의 외부 부작용을 보장하지 않는다.
